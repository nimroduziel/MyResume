Two clients, same servers

OpenWebUI

Wired up as an MCP client so chat users get Confluence, Jira and GitLab context inside ordinary conversations, without leaving the UI.

Claude Code

Engineers' Claude Code sessions are configured against the same three servers. So an engineer at the CLI and a chat user in the browser are hitting one shared set of tool servers — one place to deploy, upgrade and secure them.

Worth noting about the topology: these tool servers are shared rather than duplicated per client, so both surfaces stay in step automatically — one place to deploy, upgrade and secure them. The flip side is that they were sized for a tool-call workload rather than for redundancy, which puts replication on the roadmap alongside the retrieval models.

How this fits the wider platform

MCP traffic is separate from inference traffic. A request to a model goes through LiteLLM; a request for a Jira ticket goes straight to the Jira MCP pod. Both clients therefore hold two independent relationships: one with the gateway, one with the tool servers. Only the model path crosses into the segregated network — MCP calls stay entirely within the cluster network.

Generalized reference architecture. Component counts, model choices and topology are illustrative of the design pattern rather than a description of any live deployment; hostnames, addresses, ports and environment specifics are deliberately omitted.
