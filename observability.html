Why OpenTelemetry is in the picture

The OTel Collector is not a general-purpose tracing backbone here. Its whole purpose is narrow and specific: take the metrics OpenWebUI emits and make them Prometheus-friendly. OpenWebUI is the one component whose native metric output doesn't drop straight into a Prometheus scrape, so OTel sits in between as a translator.

Everything else — LiteLLM and all eleven vLLM containers — is scraped by Prometheus directly. Only OpenWebUI takes the detour through OTel.

What Prometheus scrapes

TargetLocationPath
LiteLLM (5 pods)Cluster network · in-clusterScraped directly
OpenWebUI (3 pods)Cluster network · in-clusterVia the OTel Collector
All vLLM instances (11 containers on 9 VMs)Segregated network Scraped directly, across the network boundary
Grafana (consumer, not a target)External · shared instance Queries Prometheus as a datasource; dashboards only

That cross-network scrape is worth calling out: Prometheus lives in the cluster but reaches out to the GPU fleet on the other network, which is one of the specific flows the inter-network rules are there to permit.

Grafana — dashboards, but not ours to run

Grafana is not part of this platform's deployment. It is a central, shared instance that already existed and is operated by someone else; what belongs to this platform is the set of dashboards built inside it for OpenWebUI, LiteLLM and the vLLM fleet. That is why it is drawn with a dashed border everywhere on this site.

The connection is a Prometheus datasource: Grafana queries Prometheus when a dashboard loads, rather than Prometheus pushing anything out. The arrow is drawn in the direction the metrics travel, but the request originates at Grafana.

Because Grafana lives outside this platform's control, its availability and access model are someone else's to manage — while the dashboards themselves depend on this platform's Prometheus. Worth knowing which half of that picture you own when a dashboard looks wrong.

Alerting

Alertmanager consumes Prometheus and fires when something goes down. That's the stated scope — availability alerting over the platform's components, rather than deep SLO or capacity alerting.

What this gives you

  • Gateway-level visibility — LiteLLM metrics cover every request in the platform, since all traffic funnels through it.
  • Per-model visibility — scraping each vLLM container individually means per-container GPU and throughput data, not just an aggregate. On the VM that hosts two containers, each is a separate scrape target.
  • User-facing visibility — OpenWebUI metrics, once normalized, land in the same Prometheus as everything else.
  • Dashboards without owning the tool — the Grafana instance is shared and external; only the dashboards for these apps belong to this platform.

Generalized reference architecture. Component counts, model choices and topology are illustrative of the design pattern rather than a description of any live deployment; hostnames, addresses, ports and environment specifics are deliberately omitted.
