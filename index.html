Redundancy posture

Replica counts vary by tier. The interesting engineering point is that redundancy was applied where load demanded it, not uniformly — which leaves a deliberate, known set of single-instance components as the next thing to address.

TierPosture
Gateway and chat UIHorizontally replicated, with a clustered cache so any replica can serve any session
Relational statePrimary plus streaming replicas, fronted by a connection pooler on every node
Workflow automationReplicated control plane and worker pool
Chat modelsMultiple interchangeable instances; the gateway can route around a failed one
Vector searchClustered, load-balanced, but with no spare node
Retrieval models, tool servers, monitoringSingle-instance — capacity was never the constraint here, so replication was not prioritised
The design insight worth stating plainly: chat inference is the well-replicated part, because that is where the load is. The retrieval path and the monitoring stack are not, which means RAG availability and observability are both weaker than the headline chat capacity suggests. Replicating those is the top item on the roadmap — and an observability stack that can fail without announcing it is the kind of gap worth designing out rather than discovering.

What crosses the network boundary

The cluster and the compute VMs sit on separate, segmented networks. Only these flows are permitted across the boundary — everything else stays inside its own segment.

From (cluster)To (segregated network)Purpose
LiteLLMvLLM containersAll model inference — the only path to a GPU
OpenWebUIQdrant via HAProxyVector search for RAG
OpenWebUI, LiteLLMpgpool, platform clusterRelational state, separate database each
n8npgpool, n8n clusterWorkflow state
PrometheusvLLM instancesMetrics scraping

The important property is the shape of this list: it is short, and every entry is a named service pair with a single purpose. Nothing in the cluster reaches a GPU except through the gateway.

The shape of it in one paragraph

LiteLLM is the hinge. Every model in the estate — four Qwen3.6-35B-A3B deployments, five gemma-4-26B-A4B deployments spread across four VMs, and an embedding/reranking pair — is registered in the LiteLLM config, so nothing talks to a GPU VM directly. Three things call it: OpenWebUI for chat users, Claude Code for engineers who self-serve their own keys and get served by the same local models, and n8n for LLM steps inside automations. OpenWebUI and Claude Code also share the same three MCP servers. OpenWebUI additionally reaches Qdrant for RAG and an S3-compatible store for document uploads, and both it and LiteLLM keep relational state in a shared pgpool Postgres cluster — one database each. n8n has its own separate pgpool cluster.
