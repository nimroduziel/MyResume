One serving instance per VM, not two. Every multi-GPU model VM shards a single model across both GPUs via tensor parallelism — trading replica count for larger effective context and higher per-request throughput. The embedding/ranking VM is the sole exception, because two distinct 8B models each fit comfortably on one L40.

Runtime and transport

  • Every GPU VM runs vLLM inside a Docker container, listening on OpenAI-compatible API and exposing an OpenAI-compatible API.
  • The VMs sit on a separate, segmented network from the cluster, with only the specific service-to-service flows permitted across the boundary.
  • Model selection, fallbacks and load balancing are all expressed in the LiteLLM config, which is the authoritative registry of what exists.

Two client surfaces, one backend

OpenWebUI

Authenticates to LiteLLM with an API key. Chat users never see the model fleet; they pick from LiteLLM's model aliases. OpenWebUI also uses the embedding and ranking models — via the same gateway — to power RAG over Qdrant.

Claude Code

Claude Code is fully supported across the network. Engineers who install it self-serve their own API key in LiteLLM and point the CLI at the gateway. Those requests are served by the local self-hosted models — the traffic never leaves for the real Anthropic API. Claude Code sessions can also call the MCP servers directly.

Generalized reference architecture. Component counts, model choices and topology are illustrative of the design pattern rather than a description of any live deployment; hostnames, addresses, ports and environment specifics are deliberately omitted.
