Request Walkthroughs

The other pages show what is connected to what. These show what actually happens, in order, for the three ways work enters the platform.

If you only read one thing on this site, read Flow 1. It touches every component — LiteLLM, both model types, Qdrant, S3 and Postgres — in a single request.

Flow 1 — A chat user asks a question about a document

The full RAG path. Note that OpenWebUI never talks to a GPU directly: embedding, reranking and chat completion are all LiteLLM calls, just to different models.

  W-->>U: Answer with citations

Three different models are used in one request, all through the same gateway. Steps 1–7 only run when a new document is uploaded.

Flow 3 — An n8n automation calls a model

n8n is the third LiteLLM consumer. It is also the only workload using the second pgpool Postgres cluster.

sequenceDiagram
  autonumber
  participant T as Trigger
  participant M as n8n Master
  participant K as n8n Worker
  participant L as LiteLLM
  participant F as vLLM Fleet
  participant P as n8n Postgres

  T->>M: Schedule or webhook fires
  M->>P: Record the execution
  M->>K: Dispatch the job
  K->>L: LLM step inside the workflow
  L->>F: Route to a local model
  F-->>L: Completion
  L-->>K: Completion
  K->>P: Persist the result
  K-->>M: Job complete

n8n's state lives in its own Postgres cluster, entirely separate from the one OpenWebUI and LiteLLM share.

What the three flows have in common

  • Every model call goes through LiteLLM. Three different entry points, one gateway, one place where keys, rate limits, routing and spend are enforced.
  • Nothing but LiteLLM opens OpenAI-compatible API. That is the only reason the cluster needs to reach the GPU network for inference at all.
  • MCP traffic is not model traffic. It never touches the gateway, and it never leaves the cluster network.
  • Each consumer owns its own durable state — OpenWebUI and LiteLLM in separate databases on the platform cluster, n8n on its own cluster.

Generalized reference architecture. Component counts, model choices and topology are illustrative of the design pattern rather than a description of any live deployment; hostnames, addresses, ports and environment specifics are deliberately omitted.
