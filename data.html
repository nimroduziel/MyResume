Data Layer

Four distinct stores with four distinct jobs: Postgres for durable relational state, Qdrant for vector search, S3 for uploaded documents, Redis for in-cluster coordination.

The Qdrant master and worker also replicate between themselves; that link is omitted here so the client-facing paths stay clear.

Qdrant vector cluster

  • 2 VMs, each with 2 × T4 GPUs — one runs the master, one runs the worker.
  • The T4s are not idle: they drive Qdrant's GPU-accelerated indexing, which is what keeps index builds off the CPU as the corpus grows.
  • HAProxy fronts the cluster and load-balances across the instances, so clients address one endpoint rather than individual nodes.
  • OpenWebUI is the only consumer, using it as the vector DB behind RAG. It reaches HAProxy across the the cluster network → the segregated network boundary.

Postgres: two separate pgpool clusters

Relational state lives on the segregated network, not in the cluster. There are two independent pgpool Postgres clusters — the platform's own, and a dedicated one for n8n.

Both clusters are addressed through pgpool, never by connecting to a Postgres node directly.

  • Platform cluster — 3 VMs on the segregated network. Every VM runs both pgpool and a Postgres instance: one primary with two streaming replicas. Clients connect to pgpool.
  • Two databases, one cluster. OpenWebUI and LiteLLM each get their own separate database inside it — shared infrastructure, isolated schemas.
  • n8n has its own cluster, also pgpool-fronted and also on the segregated network, kept entirely separate from the platform's.
Three storage tiers, three jobs. Postgres holds durable relational state (users, chats, keys, spend, workflows). Redis holds ephemeral shared state so replicas can coordinate. Qdrant holds vectors. Losing Redis is a performance and session problem; losing Postgres is a data problem.

Object storage

An on-prem S3-compatible object store (MinIO-style, not AWS). OpenWebUI connects to it for user document uploads — this is where the raw files land before their embeddings end up in Qdrant.

Redis: two independent clusters

ClusterPodsServesWhy it exists
OpenWebUI Redis6OpenWebUI (3 pods) Shared state so any replica can serve any user session
LiteLLM Redis6LiteLLM (5 pods) Shared key, rate-limit and routing state across the gateway replicas
These two Redis clusters are deliberately separate — same technology, no shared state, independent Helm releases. A LiteLLM cache problem cannot take down user sessions in OpenWebUI, and vice versa.

The RAG path, end to end

  1. A user uploads a document in OpenWebUI → the file is stored in the S3-compatible store.
  2. OpenWebUI requests embeddings through LiteLLM, which routes to llama-embed-nemotron-8b on the GPU fleet.
  3. Vectors are written to Qdrant through HAProxy.
  4. At query time, OpenWebUI searches Qdrant, optionally reranks candidates with llama-nemotron-rerank-1b-v2, then sends the assembled prompt to a chat model — all through the same LiteLLM gateway.
